## 0. What passing means

| § | Threshold (plan §2.2) | Why it matters |
|---|---|---|
| **S** | ≥ 99 % of TRACK setpoints equal SUPER's command under (x, −y, −z), ψ → −ψ | the bridge still converts correctly when the follower, not a click, is driving |
| **G** | ≥ 99 % of `/planning/follow_goal` answered on `/planning/goal_status` ≤ 0.2 s, `requested_p` ≤ 1 cm | `follow_planner` correlates on `requested_p`; a stale SUPER patch fails this silently |
| **A** | `/dtp/abort` → NAV_LAND ACCEPTED ≤ 1.0 s → `nav_state` AUTO_LAND, with **both** bridges still publishing (the offboard bridge: its heartbeat, since 2026-09-28) | the third writer wins against the two bridges |
| **T** | 3/3 ch11 takeovers: out of OFFBOARD ≥ 2 s while the bridge keeps its heartbeat up; since 2026-09-28 also its setpoints stop ≤ 0.25 s after each | nothing of ours takes the aircraft back |

**What PX4 does here** (from our firmware's source, `~/PX4-Autopilot` @ `d6f12ad`):
- **The Offboard switch is edge-triggered** (`ManualControl.cpp:221`). A ch11 left ON after an ABORT
  does **not** pull the aircraft back into Offboard. Flipping it OFF then ON **does**.
- **NAV_LAND is a forced mode change** (`Commander.cpp:1093`). It is accepted unless the mode
  intention itself refuses; then the ack is TEMPORARILY_REJECTED and the mux retries every 0.5 s.
- **`COM_RC_OVERRIDE = 1`, the auto bit only:**
  - in **Offboard** the sticks do nothing;
  - during the ABORT's **AUTO_LAND** they **do** take over to Position (`Commander.cpp:2946`).
- **Offboard can be entered disarmed.** RC gates arming, not the mode switch
  ([`fact-offboard-rc-arming.md`](fact-offboard-rc-arming.md)).

**After an ABORT, never re-engage ch11 without relaunching the follower.** The mux is terminal and
keeps publishing its latched HOLD goal (+0.75 m climb), which SUPER would fly to.

## 1. Preconditions

- **Props physically removed.** Not "disarmed", not "throttle low": off the motors.
- **RC bound**, `RC_MAP_OFFB_SW = 11` (listener `manual_control_switches`: `offboard_switch` 3 = OFF,
  1 = ON, 0 = NOT MAPPED). **Kill switch ch10 tested before arming.** ch5 on **Position**.
- **FC fault card empty:** `python3 scripts/px4/clear_fault_logs.py` says nothing to clear.
- **ARK's `logloader.service` is still disabled** — disabled 2026-09-13 after it looped for a day,
  see §6.
  - Check: `systemctl is-enabled logloader` says `disabled`.
  - Check: `df -h /` has ≥ 20 GB free.
- **The aircraft sits where FAST-LIO will start**, level and still (flight-test-plan §1a).

**`COM_DISARM_PRFLT = 10 s`.** Props off, PX4 never detects a takeoff and **disarms itself ~10 s
after arming**.
- Every armed trial below fits inside one 10 s window.
- Re-arm for the next trial.
- **Do not raise the parameter to make the test easier.** The windows below are enough.

## 2. Bring-up — in this order, with the check after each step

```bash
# shell 1 -- Livox + FAST-LIO + SUPER on the FOLLOW config (M5.2 envelope, M5.3a filter block)
SUPER_CONFIG=follow_test_ros2.yaml RVIZ=false bash scripts/run.sh   # FASTLIO_DDS_PROFILE=nonblocking is the default
#   check: its log prints "fsm_node on follow_test_ros2.yaml"; odom >= 9.5 Hz
#   (or the web GCS: Stack row, "follow" chip, Start -- the default chip is still click)

# shell 2, 3 -- both bridges (never children of run.sh; stop them explicitly), off FAST-LIO's cores
taskset -c 0-5 ros2 run super_bringup px4_odom_bridge.py        # want guard=TRACKING, in=out, rejected=0
taskset -c 0-5 ros2 run super_bringup px4_offboard_bridge.py    # want IDLE, sp_out 0 "(withheld: PX4 not in Offboard)" until ch11 (since 2026-09-28)

# shell 4 -- the DTP follower, LIVE, riding on shell 1 (never a second driver or fsm_node)
source ~/super_ws/src/drone-dtp/ros2_ws/dtp_env_jetson.sh      # libcudss for the GPU cloud
ros2 launch dtp_bringup dtp_system.launch.py lidar:=false super:=false observe_only:=false \
    config_name:=follow_test_ros2.yaml
#   (same thing: DTP_MODE=live bash scripts/dtp_follower.sh, or the web GCS's DTP follower
#    row, "Live", behind Admin control -- both refuse unless fsm_node is on the follow config)
#   check its log: "GPU cloud verified against numpy", static_calib_tf "extrinsic verified",
#   command_mux "ABORT armed"
```

**`sudo jetson_clocks`** first if the Jetson rebooted. The Stage B preflight refuses an unpinned GPU.

**CPU pinning is on by default since 2026-09-13 (M5.3):** `run.sh` puts FAST-LIO on cores 6,7 and
the Livox driver + `fsm_node` on 0-5, `dtp_follower.sh` puts the whole DTP tree on 0-5, and the GCS
starts the bridges the same way. Check with `grep Cpus_allowed_list /proc/<pid>/status`:
`fastlio_mapping` must say `6-7`, everything else `0-5`. `FASTLIO_CPUS=` (empty) turns it off.

**Bench rehearsal in one command (2026-09-14):** `bash drone-dtp/scripts/bench_bringup.sh` does
§2 in this order, observe-only, runs §3's two preflights plus rate, stamp-lag, foreign-subscriber
and CPU checks, drives the M6 oracle with synthetic coasts, records a bag, and stops everything by
process group. Its output is the record; it never arms.

## 5. The trials

Engage FOLLOW once, with the walker at **4–6 m and moving** (0.4 m of travel in 6 s is required to
lock):

```bash
ros2 param set /target_manager follow_enabled true      # wait for /dtp/lock_state LOCKED
```

The mux publishes nothing until one fully healthy tick has passed. Anyone within 1.5 m of the
commanded path holds it in `HOLD|PROXIMITY`, including the operator sitting beside the rig (§7).

Each trial is **one arm cycle, ≤ 10 s armed**. Pilot: arm in Position, flip ch11 ON.

| # | Trial | Pilot | Operator | Walker | Feeds |
|---|---|---|---|---|---|
| 1–4 | follow | arm → ch11 ON → wait for self-disarm | watch `/mux/state` FOLLOW | walk slowly across, 4–6 m | S, G |
| 5–7 | takeover | arm → ch11 ON → after ~3 s, ch11 **OFF**; hold OFF ≥ 3 s | note the time | keep walking | **T** (3 needed), S, G |
| 8 | ABORT | arm → ch11 ON | at ~2 s, `kill -STOP <perception_node pid>`; after NAV_LAND, `kill -CONT` | keep walking | **A** |

- **Trial 8** makes `/dtp/targets` go silent → `TARGETS` veto → 2.0 s → ABORT → NAV_LAND →
  AUTO_LAND → PX4's land detector disarms on the ground.
- **After trial 8, relaunch the DTP follower** (Ctrl-C shell 4, start it again, re-engage) before
  any further trial. The mux is terminal.
- **Motors will spin up to ~`MPC_THR_HOVER` (0.41)** the instant Offboard engages armed. That is
  the position controller's feedforward, not a fault (M3).

## 6. Score, then shut down

```bash
kill -INT <recorder pid>
python3 scripts/px4/m51_one_graph_check.py $D          # exit 0 = M5.1 passed
```

**Stop in reverse:** follower (Ctrl-C shell 4) → offboard bridge → odom bridge → `run.sh`.

**Then scan the card:** `python3 scripts/px4/clear_fault_logs.py`. Arming and Offboard exercise
the XRCE link the hardfault lives on.

**Why the logloader check is in §1 (found 2026-09-13).** ARK OS's `logloader.service` had been
re-uploading **one ULog (`LOG0135_2026-09-12T23:03:08Z.ulg`) every ~2 s since 2026-09-12 19:03**:
- ~14,800 copies, **241 GB** in `/var/lib/ark-os/flight-review`, ~500 MB/min;
- about 42 % of a core for logloader alone.

During the bench soak below, `/lidar_slam/odom` arrived **3.9 s late in one burst** at two
independent subscribers, stamps on time. That is the signature of the whole Jetson stalling.
EKF2 would reject that much delayed vision.

**It was stopped here, came back after a reboot, and is now fixed.**
- **Disabled 2026-09-13 16:27.** The cause is a logloader bug: it fetched LOG0135 while PX4 was
  still writing it, then could never mark the finished log uploaded.
- **The stuck database row is fixed.**
- **21,021 sha256-verified duplicates deleted**, 364.8 GB freed.
- **The FC's complete copy of the log kept.**

Full record: [`fact-ark-logloader-loop.md`](fact-ark-logloader-loop.md). Whether that loop explains
09-12's undiagnosed odometry-age problem is in §7.

**One casualty, and a trap to remember.** The bag's recorder died at 04:20:46 with `SQLite error (5):
database is locked`. That was the moment its `.db3` was read with `sqlite3` while still recording.
- **Every analysis script in this repo reads `.db3` directly.** Never run one on a bag that is
  still being recorded.
- The bag (04:11:07–04:20:46) was recovered with `ros2 bag reindex <dir> -s sqlite3`.
